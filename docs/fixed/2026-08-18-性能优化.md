## 二、C19 `strip_inline_markup`：O(n²) → O(n)

### 现象

每遇到一个 `[` 就往后线性找 `]`，找不到就 `i += 1` 再来一遍。一串未匹配的
`[` 就是二次方。这条路在**每条 QQ 出站消息**上（`markdown_to_plain` →
`strip_inline_markup`）。

### 实测

`cargo test --lib scaling_probe -- --ignored --nocapture`。看倍率不看绝对值——
绝对值跟机器走，倍率不跟。

| 未匹配 `[` 数 | 改前 | 改后 |
|---|---|---|
| 1,000 | 1.55 ms | 0.29 ms |
| 2,000 | 5.67 ms | 0.25 ms |
| 4,000 | 22.46 ms | 0.50 ms |
| 8,000 | 89.58 ms | 0.59 ms |
| 16,000 | **358.51 ms** | **0.98 ms** |

每翻倍的倍率：**4.00×**（教科书级二次方）→ 约 2×。16k 那档快 **366 倍**。

### 改法

预扫一遍 `]` 与 `)` 的位置，用两个**单调游标**取「第一个 ≥ from 的位置」。
`i` 只增不减，所以游标只前进不回退，整趟 O(n)。

### 怎么证明结果没变

这条决定用户在 QQ 里看到的每一个字，手挑几条断言守不住。把**旧实现逐字抄进
测试当预言机**：

- 19 条手挑边界：嵌套、未闭合、空 URL、URL 与文本相同、中文、末尾截断
- 5,000 条确定性伪随机组合（固定种子，可复现）

逐条比对逐字节相等。

## 三、C17 知识库检索：挪出异步线程

### 现象

`keyword_search` 对库里**每个**文件做「整读 + 整份 lowercase 拷贝」，是**无界**
的（跟库大小成正比）；而它直接在 `async fn search_existing` 里同步跑——整段
时间一个 tokio worker 被占死。

### 实测

规模与耗时（`keyword_search_scaling`）：

| 库总量 | 搜索耗时 |
|---|---|
| 0.6 MB | 5.3 ms |
| 1.6 MB | 11.9 ms |
| 3.1 MB | 22.8 ms |
| 6.2 MB | 45.4 ms |

线性，约 **7.3 ms/MB**。100 MB 的库 = 约 700 ms 的运行时冻结。

真正要证明的不是搜索变快（活儿一样多），而是**搜索期间别的异步任务还转不转**
（`keyword_search_does_not_freeze_the_runtime`，单 worker 运行时 + 5ms 心跳，
6MB 库）：

| | 心跳最长被堵 |
|---|---|
| 同步跑（改前） | **41 ms** |
| `spawn_blocking`（现在） | **6 ms** |

搜索自身墙钟不变（四个档位都在 ±3% 噪声内）。

### 改法

挪进 `spawn_blocking`。算什么、算多久一个字节没变，只是不再占着异步线程。
循环只依赖 `list()` 的结果和两个配置数值，全部拷进闭包，不必让闭包借到
`&self`。

### 栽过的一次：探针没有区分能力

第一版探针**两边都量出 6 ms**，看着像「改了没用」，差一点得出「无收益，不
合并」的相反结论。

原因：搜索写在 `runtime.block_on` 的 future 里，而那是在**调用线程**上执行的，
跟 worker 上的心跳根本不抢同一个线程。把搜索也放进 `tokio::spawn` 之后才显出
41 ms vs 6 ms。

这正是 AGENTS.md 2.3 那类——**验证本身没有区分能力**，绿的和红的长得一样。
写性能探针尤其容易踩：测量装置和被测对象之间的调度关系必须先想清楚。

## 四、C12 `AppConfig` 深拷贝：量了，大改不做

方案要把 `AppConfig` 全面改成 `Arc` 快照 + 原子替换 + 版本号，牵动配置热重载
的并发。动手前先量入场费（`config::scaling_probe`）：

| | |
|---|---|
| 合成配置（22 供应商 × 3 模型） | 序列化 12 KB，单次 clone **27.8 µs** |
| 实际配置（`~/.miyu/config/config.jsonc`） | 23.7 KB，按比例约 **55 µs** |
| 一条消息按 3 次拷贝算 | 约 165 µs |
| 1000 条/分钟的群 | 约 165 ms/分钟 ≈ **0.3% 单核** |

**结论：不做。** 0.3% 的收益换一次牵动热重载并发的大改，不划算——按方案自己
第 3 节那条「若某项优化实测无明显收益，先不合并，避免徒增复杂度」。

### 但白捡的那部分做了

`handle_message_with_activity` 原来**第一件事**就是深拷贝整份配置，然后才检查
「是不是自己发的」「是不是私聊/群聊事件」「平台开没开」。也就是说每条被丢弃
的事件——机器人自己的消息、各类通知事件、平台关掉时的一切——都白付一次拷贝。

把不需要配置的判断提到拷贝之前，平台开关的检查放进同一个锁作用域里先看一眼
bool。被丢弃的事件从此零拷贝，正常消息的路径一个字节没变。

这条的教训是：**同一个「热点」里，代价高的部分和好摘的部分往往不是一回事。**
先量，再挑那颗真的低垂的果子。

## 五、量尺的约定

所有 `scaling_probe` / 探针类测试都标 `#[ignore]`，平时不进测试套：

```bash
cargo test --lib <模块>::scaling_probe -- --ignored --nocapture
```

它们是**量尺，不是断言**。时间断言在不同机器/负载下必然抖，写进测试套只会
制造假红。要断言的是**结果不变**（差分测试），不是耗时。
