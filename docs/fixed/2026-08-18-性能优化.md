## 二、C19 `strip_inline_markup`：O(n²) → O(n)

### 现象

每遇到一个 `[` 就往后线性找 `]`，找不到就 `i += 1` 再来一遍。一串未匹配的
`[` 就是二次方。这条路在**每条 QQ 出站消息**上（`markdown_to_plain` →
`strip_inline_markup`）。

### 实测

`cargo test --lib scaling_probe -- --ignored --nocapture`。看倍率不看绝对值——
绝对值跟机器走，倍率不跟。

| 未匹配 `[` 数 | 改前 | 改后 |
|---|---|---|
| 1,000 | 1.55 ms | 0.29 ms |
| 2,000 | 5.67 ms | 0.25 ms |
| 4,000 | 22.46 ms | 0.50 ms |
| 8,000 | 89.58 ms | 0.59 ms |
| 16,000 | **358.51 ms** | **0.98 ms** |

每翻倍的倍率：**4.00×**（教科书级二次方）→ 约 2×。16k 那档快 **366 倍**。

### 改法

预扫一遍 `]` 与 `)` 的位置，用两个**单调游标**取「第一个 ≥ from 的位置」。
`i` 只增不减，所以游标只前进不回退，整趟 O(n)。

### 怎么证明结果没变

这条决定用户在 QQ 里看到的每一个字，手挑几条断言守不住。把**旧实现逐字抄进
测试当预言机**：

- 19 条手挑边界：嵌套、未闭合、空 URL、URL 与文本相同、中文、末尾截断
- 5,000 条确定性伪随机组合（固定种子，可复现）

逐条比对逐字节相等。

## 三、C17 知识库检索：挪出异步线程

### 现象

`keyword_search` 对库里**每个**文件做「整读 + 整份 lowercase 拷贝」，是**无界**
的（跟库大小成正比）；而它直接在 `async fn search_existing` 里同步跑——整段
时间一个 tokio worker 被占死。

### 实测

规模与耗时（`keyword_search_scaling`）：

| 库总量 | 搜索耗时 |
|---|---|
| 0.6 MB | 5.3 ms |
| 1.6 MB | 11.9 ms |
| 3.1 MB | 22.8 ms |
| 6.2 MB | 45.4 ms |

线性，约 **7.3 ms/MB**。100 MB 的库 = 约 700 ms 的运行时冻结。

真正要证明的不是搜索变快（活儿一样多），而是**搜索期间别的异步任务还转不转**
（`keyword_search_does_not_freeze_the_runtime`，单 worker 运行时 + 5ms 心跳，
6MB 库）：

| | 心跳最长被堵 |
|---|---|
| 同步跑（改前） | **41 ms** |
| `spawn_blocking`（现在） | **6 ms** |

搜索自身墙钟不变（四个档位都在 ±3% 噪声内）。

### 改法

挪进 `spawn_blocking`。算什么、算多久一个字节没变，只是不再占着异步线程。
循环只依赖 `list()` 的结果和两个配置数值，全部拷进闭包，不必让闭包借到
`&self`。

### 栽过的一次：探针没有区分能力

第一版探针**两边都量出 6 ms**，看着像「改了没用」，差一点得出「无收益，不
合并」的相反结论。

原因：搜索写在 `runtime.block_on` 的 future 里，而那是在**调用线程**上执行的，
跟 worker 上的心跳根本不抢同一个线程。把搜索也放进 `tokio::spawn` 之后才显出
41 ms vs 6 ms。

这正是 AGENTS.md 2.3 那类——**验证本身没有区分能力**，绿的和红的长得一样。
写性能探针尤其容易踩：测量装置和被测对象之间的调度关系必须先想清楚。

## 四、C12 `AppConfig` 深拷贝：量了，大改不做

方案要把 `AppConfig` 全面改成 `Arc` 快照 + 原子替换 + 版本号，牵动配置热重载
的并发。动手前先量入场费（`config::scaling_probe`）：

| | |
|---|---|
| 合成配置（22 供应商 × 3 模型） | 序列化 12 KB，单次 clone **27.8 µs** |
| 实际配置（`~/.miyu/config/config.jsonc`） | 23.7 KB，按比例约 **55 µs** |
| 一条消息按 3 次拷贝算 | 约 165 µs |
| 1000 条/分钟的群 | 约 165 ms/分钟 ≈ **0.3% 单核** |

**结论：不做。** 0.3% 的收益换一次牵动热重载并发的大改，不划算——按方案自己
第 3 节那条「若某项优化实测无明显收益，先不合并，避免徒增复杂度」。

### 但白捡的那部分做了

`handle_message_with_activity` 原来**第一件事**就是深拷贝整份配置，然后才检查
「是不是自己发的」「是不是私聊/群聊事件」「平台开没开」。也就是说每条被丢弃
的事件——机器人自己的消息、各类通知事件、平台关掉时的一切——都白付一次拷贝。

把不需要配置的判断提到拷贝之前，平台开关的检查放进同一个锁作用域里先看一眼
bool。被丢弃的事件从此零拷贝，正常消息的路径一个字节没变。

这条的教训是：**同一个「热点」里，代价高的部分和好摘的部分往往不是一回事。**
先量，再挑那颗真的低垂的果子。

## 五、M4-1 登录限流表：无界增长（网络侧）

### 现象

`WebAuth::attempts` 是 `HashMap<IpAddr, LoginAttempt>`，靠 `entry().or_insert()`
增长，**从不清理**。窗口过期的条目留着，失败过的条目也留着。

IPv6 的一个 /64 里有 2⁶⁴ 个地址，随手轮换。每个新地址插一条（约 60–80 字节
含 HashMap 开销），几十万次尝试就是几十 MB——这是暴露在网络侧的内存耗尽入口。

### 改法

三层，顺序有讲究：

1. **IPv6 按 /64 前缀归并**。/64 在现实里就是同一个来源，业界限流也按它算。
   归并之后轮换地址不再产生新条目，限流本身还更严。
2. 表满时**先清过期条目**（窗口过了的条目下面本来就会被重置，删掉无损）。
3. 清完仍满则**拒绝新来源**，不淘汰活跃条目。

第 3 条是关键：如果满了就淘汰最旧的活跃条目，攻击者只要刷满表就能把自己
「正在被限」的记录挤掉，计数归零——那等于把限流本身送掉了。宁可让新来源在
极端拥塞下走 `RateLimited`，也不能开这个口子。

### 验证

三条用例，其中第一条撤掉修复后报红：

| 用例 | 有修复 | 撤掉 /64 归并 |
|---|---|---|
| 同一 /64 打 10,000 次，表里的条目数 | **1** | **4096**（撞到容量上限；没有上限时就是 10,000） |
| 8 个不同 /64 分别记 | 8 | — |
| 灌 4,596 个新来源后，被限的 IP 仍被限 | 是 | — |

第三条守的正是上面那个绕过路径。

### 取舍

同一个 /64 下的两个人共用一个计数桶。个人助手的 Web 界面里这是可接受的，
也是标准做法。

## 六、M4-4 / M4-3：两处只增不减的结构

### M4-4 封禁理由历史

`update_offender` 里，外层「每群被禁者」map 早有上限
（`max_offender_history_per_group`，500），但**每个人的 `reason_history` 只
push 不裁**。同一个人被禁一千次就存一千条，而这份记录每次封禁都要整块 JSON
读改写——越长越慢也越占。

加 `MAX_REASON_HISTORY_PER_OFFENDER = 50`，裁掉最旧的。选 50 的理由：这份历史
是给「屡犯判定」和历史查询用的，同一个人在同一个群里被禁 50 次早就够判定了，
更早的记录对决策没有增量。最坏体积 = 500 人 × 50 条。

### M4-3 天气缓存

`write_cache` 每次写入会 `retain` 清掉过期条目，但**没有条数上限**。TTL 只挡得
住「同一个地名反复查」，挡不住「短时间内查一堆不同地名」——那种情况下条目
全在 TTL 内，一条都不会被清掉。

加 `MAX_CACHE_ENTRIES = 512`，超了淘汰最旧的。键是地名/坐标，丢了只是下次重
查一次。

两条各一个用例：写入 3 倍上限的量，断言**每一次写入之后**都不超上限，且留下
的是最近那批。

## 七、M2 `append_tool_report`：已量，修法要动表结构

### 现象

每追加一条报告都是「读整列 → 解析 → push → 整个序列化 → 写回」。一个回合里
N 次工具调用，写回字节数是 O(N²)。

### 实测

`state::tests::turns::tool_report_write_amplification`，单条报告 2 KB：

| 报告数 | 理论写入 | 实际写入 | 放大 | 耗时 |
|---|---|---|---|---|
| 10 | 20 KB | 110 KB | 5.5× | 3.8 ms |
| 20 | 40 KB | 420 KB | 10.5× | 13.8 ms |
| 40 | 80 KB | 1,640 KB | 20.5× | 51.9 ms |
| 80 | 160 KB | 6,480 KB | **40.5×** | **210.7 ms** |

耗时是二次方（每翻倍约 4×）。

### 为什么还没修

干净的修法是把 `tool_reports` 从「turns 表里的一个 JSON 数组列」改成**追加型
子表**，那样每次 append 是一条 INSERT，O(1)。但这要：

1. 加一版 schema migration（当前 v24）；
2. 迁移既有数据；
3. 改所有读取方（`attach_turn_children_locked`、`load_visible_turns` 等）。

属于要单独评审的改动，且典型回合只有 3–10 次工具调用（放大 5.5×、约 4 ms，
可以忽略）。真正吃亏的是 `deep_research`、长 agentic 回合这类几十次工具调用的
场景。**等确认要做再动。**

所有 `scaling_probe` / 探针类测试都标 `#[ignore]`，平时不进测试套：

```bash
cargo test --lib <模块>::scaling_probe -- --ignored --nocapture
```

它们是**量尺，不是断言**。时间断言在不同机器/负载下必然抖，写进测试套只会
制造假红。要断言的是**结果不变**（差分测试），不是耗时。

## 八、M3 孤儿 keepalive 任务：不只是内存，是在花钱

### 现象

`start_cache_keepalive` 用 `tokio::spawn` 起一个循环，按 `keepalive_seconds`
定期给供应商发一次带完整前缀的请求，把前缀缓存续上。循环只认一个
`Arc<AtomicBool>` 取消标志。

取消只在**新回合开始**时调用（`chat_stream_turn` / `redo_stream_turn`），而
`Agent` **没有 `Drop` 实现**。于是：

- 回合结束、会话切换、平台回合收尾 → `Agent` 被丢掉 → 没人翻标志
- 循环继续跑，直到 `keepalive_max_pings`（默认 20）耗尽
- **每次 ping 都是一次真实的 LLM 请求**——不是内存问题，是账单问题

平台回合尤其中招：每个平台回合用的是临时 `Agent`，跑完就丢，那条路上永远
轮不到取消。

### 现在没在花钱

`cache.keepalive_seconds` 默认 **0（关闭）**，用户配置里也没开。所以这是一个
**潜伏**的 bug——谁开谁中。

### 改法

给 `Agent` 加 `Drop`，翻取消标志。四行。

### 验证

`dropping_the_agent_stops_the_keepalive_loop`：打开 keepalive、塞一份请求快照
（没有快照 `start_cache_keepalive` 直接返回）、起循环、克隆取消标志、
`drop(agent)`、断言标志已翻。

撤掉 `Drop` 之后报红：

```
Agent 被丢掉之后 keepalive 必须停——否则它会继续发请求计费
```

### 剩下的 M3

方案还提「快照只存序列化字节 `Arc<Vec<u8>>`」「每 turn 只保留一份」。那是省
内存的部分，还没量——`last_request_snapshot` 持有整段消息（含 base64 图片），
值不值得改要先量它实际多大。

## 九、M4-5 任务日志：整读改 seek

### 现象

`read_log_slice`（增量追新输出）和 `read_log_tail`（看最近几行）都是
`std::fs::read(path)` **整读**，再从里面切一小段。返回的内容是固定几 KB，
代价却跟日志总大小成正比——而长跑任务的日志正是会长到几十上百 MB 的那种。

### 实测

`jobs::output::scaling_probe`：

| 日志大小 | 增量读（改前 → 改后） | 取尾部（改前 → 改后） |
|---|---|---|
| 1 MB | 0.08 → 0.01 ms | 1.66 → 0.18 ms |
| 4 MB | 1.29 → 0.00 ms | 7.60 → 0.16 ms |
| 16 MB | 2.96 → 0.00 ms | 26.56 → 0.17 ms |
| 64 MB | **25.72 → 0.00 ms** | **120.49 → 0.16 ms** |

从**线性变成常数**。注意 64MB 那行的增量读：一个新字节都没有，也要 25.7 ms。

### 改法

- `read_log_slice`：`seek(offset)` 之后只读 `budget` 字节，`size` 从 metadata 拿。
- `read_log_tail`：从尾部取 64 KB 窗口；窗口内的完整行数不够就翻倍，上限是
  整个文件。绝大多数情况第一次就够。

窗口版有两个坑，都处理了：

1. 窗口不是从头开始时，**第一行多半是被切断的半行**，要丢掉。
2. 「要不要省略号」和「从第几行开始」是两件事。整读版靠 `start > 0` 判断，
   因为它手里就是全文；窗口版即便窗口内恰好只剩 `lines` 行（`start == 0`），
   只要窗口没读到文件头，前面就一定还有内容，省略号照补。第一版我图省事写成
   `start.max(1)`，那会多吃掉一行。

### 验证

拿整读版当预言机做差分，9 种日志形状 × 4 种 `lines` × 5 种 offset × 4 种
budget：空文件、单行、无末尾换行、恰好 20 行、21 行、超长行、远超首窗的
CJK 大文件、非法 UTF-8 字节、连续空行。全部逐字节一致。

## 十、M4-6 / M4-7：量了，都不做

这两条方案说得没错，但**量出来都不到 5 ms**，改动却各有风险。按方案第 3 节
「若某项优化实测无明显收益，先不合并，避免徒增复杂度」，都不做。

### M4-6 `history(limit)`

现状属实：把整个会话的所有回合（含每个回合的子表挂载）全读出来，再取尾部
`limit` 条。

| 会话回合数 | `history(10)` 耗时 |
|---|---|
| 50 | 0.95 ms |
| 100 | 1.15 ms |
| 200 | 2.03 ms |
| 400 | **4.07 ms** |

线性，但绝对值极小；而且**唯一调用方是 `miyu history` 这条用户手敲的命令**，
一次性执行。4 ms 不值得为它加一条 `load_recent_turns` 变体和配套差分测试。

### M4-7 prune 重读已归档回合

现状比方案说的还准一点：SELECT 把每个已完成可见回合的 `tool_reports` 整块拉
出来，循环里对**已归档**的直接 `continue`。反复压缩时绝大多数回合都已归档，
等于每次把整个会话的报告读一遍再全扔掉。

| 回合数 | 首次 prune | 再次 prune（全部已归档） | 再次白读 |
|---|---|---|---|
| 50 | 2.35 ms | 0.19 ms | 270 KB |
| 100 | 5.41 ms | 0.51 ms | 570 KB |
| 200 | 10.70 ms | **1.17 ms** | **1,170 KB** |

1.17 ms。而干净的修法有个不能忽略的语义坑：不能简单加
`AND tool_reports_archive IS NULL`——`eligible = rows.len() - protect_recent`
是按「**所有**已完成可见回合」算的，把已归档的滤掉会让 `rows.len()` 变小，
protect 的就成了另一批回合。要保语义得拆成两条查询（先取保护尾部的 seq 下界，
再按下界取未归档的行）。1 ms 换这个复杂度，不划算。

**两条都留着探针**（`history_limit_scaling` / `prune_rereads_archived_turns`），
将来会话规模上一个数量级时可以直接重量。

## 十一、M3 快照体积：前提不成立，剩下那半不做

M3 说「keepalive 快照持有整段会话（含 base64 图片）常驻，ping 和工具轮多次
全量 clone」。拆开看：

### 「常驻」的前提不成立

存快照那一行是有条件的：

```rust
if self.config.cache.keepalive_seconds > 0 && responses_continuation.is_none() {
    self.last_request_snapshot = Some((request_messages.clone(), definitions.clone()));
}
```

`keepalive_seconds` 默认 **0（关闭）**。关着的时候**一份快照都不会存**，谈不上
常驻。而且它是 `Agent` 的一个字段，每轮直接覆盖——「每 turn 只保留一份」本来
就已经成立。

### clone 的代价（`keepalive_snapshot_cost`）

| 会话形态 | 快照大小 | 单次 clone | 20 次 ping 合计 |
|---|---|---|---|
| 40 轮纯文本 | 33 KB | 8.8 µs | 0.18 ms |
| 40 轮 + 1 张图 | 133 KB | 10.4 µs | 0.21 ms |
| 40 轮 + 5 张图 | 534 KB | 21.0 µs | **0.42 ms** |

### 判定：不做

方案提的「快照只存序列化字节 `Arc<Vec<u8>>`」要动请求体的构造路径，而那条路
是**字节纯度敏感**的（AGENTS.md 1.1）。用它换 0.42 ms 和最多 0.5 MB，而且只在
一个默认关闭的功能打开时才有意义——不划算。

ping 循环里的 `messages.clone()` 也不是能随手去掉的：下游
`prepare_chat_messages_for_provider` 消费 owned 消息，改成借用只会把 clone 挪
进去。

**M3 真正该修的那半已经修了**（第八节：孤儿 keepalive 任务）。那条是会花钱的
bug，和内存无关。
