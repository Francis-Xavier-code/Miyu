## 3. 依赖方向问题

用 `use crate::...` 统计出的关键跨层依赖：

```
platforms  -> web        （平台层依赖 Web daemon 内部类型）
web        -> cli        （daemon 依赖 CLI 的 WebArgs 和工具注册）
daemon     -> cli        （daemon 入口依赖 CLI 参数）
tools      -> platforms  （vision 依赖平台上下文/发送逻辑）
agent      -> platforms  （依赖平台图片/文件上下文类型）
memory     -> platforms  （依赖 PlatformPrincipal）
render     -> tools      （仅依赖 CommandOutputStream 类型）
state      -> memory     （状态层依赖 EvictedTurn）
memory     -> state      （整理器依赖 StateStore）→ 形成 state ↔ memory 循环
platforms  -> tools      （平台插件注册工具，本身合理）
platforms  -> state      （平台会话绑定/权限，合理）
```

结论：最需要处理的是 `platforms→web`、`web→cli`、`tools→platforms`、`state↔memory` 四处。

## 4. 其他可维护性问题

1. **`main.rs` 直接声明所有模块**：没有 `lib.rs`，集成测试和未来的复用都只能贴着二进制入口。
2. **`#![allow(dead_code)]` 在 crate 根**：掩盖未使用代码，影响清理与重构信心。当前用 `RUSTFLAGS='--force-warn=dead_code' cargo check --all-targets` 实测可暴露生产目标 103 条、测试目标 72 条告警；其中 `agent/conversation.rs` 整个文件、`tools/edit_replace.rs`、`tools/write.rs` 整模块未使用。完整清单与处置见 [13-死代码清理计划](13-死代码清理计划.md)。
3. **大量 `pub(crate)` 但缺少边界说明**：模块间靠隐式约定，新贡献者容易在 `platforms` 里直接用 `web` 类型。
4. **测试大块内联**：`web.rs`、`openai_compatible.rs`、`render/mod.rs`、`conversation_db.rs` 等文件中测试占比很高，阅读生产代码要跳过大量测试。
5. **“一个文件 = 一个功能”边界不清**：例如 `config.rs` 同时是 schema、默认值、校验器、模型池路由、prompt 文件管理。
6. **协议代码集中**：`openai_compatible.rs` 三协议共用大量私有 helper，新增协议必须读懂全部 8.6k 行。
7. **平台逻辑与 daemon 逻辑耦合**：OneBot 事件循环需要 `ActorCommand/RunInfo/IpcRunGuard` 等 daemon 内部概念。

## 5. 拆分时必须保护的既有契约

这些是“零行为变化”中最容易被文件移动破坏的点：

- **请求前缀字节稳定**：`agent` 的消息组装、工具目录生成、系统提示词拼接顺序，一行逻辑都不能变。
- **数据库 schema 与迁移**：`conversation.db` 的 v1–v24 迁移、固定列序 SELECT、`map_turn_row` 位置解析。
- **IPC 协议**：`ipc.rs` 的命令枚举、帧格式、错误兼容（legacy busy 消息）。
- **OneBot 协议**：CQ 解析、echo→oneshot 路由、连接代际、发送拆条行为。
- **SSE 事件名与前端**：`EVENT_NAMES` 前后端必须一致。
- **配置 JSON 结构**：`config.jsonc` 字段名、默认值、旧键迁移逻辑。
- **导出归档格式**：manifest version、unit 分类、fixups。
