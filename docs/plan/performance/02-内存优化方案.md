# 02 · 内存优化方案

## 1. 原则

- 任何长期增长的数据结构必须有容量上限、TTL 或轮转策略。
- 优先“少拷贝”，其次“有界缓存”。
- 数据库热路径避免把整列/整表 JSON 反复解析重写。
- 优化只影响内部表示，不改变导出、历史显示与数据库兼容性。

## 2. M1：usage-history.jsonl 轮转与索引

**现状**：

- `state/usage.rs` 的 `usage-history.jsonl` 只增不减；
- 每次统计 `read_to_string` 整文件 + 全量解析；
- 为取 limit 条做全量 O(n log n) 排序；
- 缓存命中仍 clone key。

**修法**：

1. 按日/按大小轮转（如 10 MiB 或 30 天），旧文件压缩成 `.gz`；
2. 统计改为 SQLite 临时表或固定 N 天聚合；明细页只读尾部 limit 条；
3. 月度/年度统计从聚合表读取；
4. 保持 `usage.json` 与明细账的现有数值语义不变。

## 3. M2：中断回合 journal 与 tool_reports 有界化

**现状**：

- 中断回合 journal 永不清除，单条上限 64 MiB；
- `load_visible_turns` 每轮全量反序列化；
- `append_tool_reports` 每条追加都整体读-解析-重写 JSON 数组，O(n²) 写放大。

**修法**：

1. journal 完成/中断后延迟清理，只保留可恢复重放所需最小事件；
2. `tool_reports` 改追加型子表或分段 BLOB，禁止整体重写；
3. `load_visible_turns` 只查询当前可见窗口所需列，并加 LIMIT/游标；
4. 保持崩溃恢复语义：保留最近一次未完成 journal，旧的只留摘要。

## 4. M3：keepalive 与请求快照

**现状**：

- keepalive 快照持有整段会话（含 base64 图片）常驻；
- ping 和工具轮多次全量 clone。

**修法**：

1. 快照只存序列化字节 `Arc<Vec<u8>>`；
2. 每 turn 只保留一份，旧的及时替换；
3. 确保 turn 结束/取消时释放快照；
4. 修复孤儿 keepalive 任务（当前 per-turn Agent 无 Drop 取消，开启 keepalive 时任务继续驻留并计费）。

## 5. M4：无界/半无界缓存清单

| # | 位置 | 现状 | 修法 |
|---|---|---|---|
| M4-1 | `web.rs` 登录限流 HashMap | IPv6 轮换可无限增长 | 固定容量 + TTL，超限淘汰最旧 |
| M4-2 | `cli.rs` clipboard_texts 磁盘缓存 | `shell_pasted_text_index` 只增不清 | 容量上限（如 100 条）+ 写入时淘汰；wake/run 集合当前已随轮询重建，无需处理 |
| M4-3 | `tools/weather.rs` 两个 static 缓存 | 过期条目已在写入时 sweep，但无容量上限 | 增加条目数上限；保留现有 sweep 逻辑 |
| M4-4 | `platforms/plugins/group_management.rs` reason_history | 高频被禁者永不淘汰 | 按配置 `max_records` 裁剪并淘汰最旧 |
| M4-5 | `tools/jobs.rs` job 日志读取 | offset 支持却整文件读入 | 按 offset 增量读、tail 用 seek |
| M4-6 | `state/mod.rs` `history(limit)` | 全量加载后取尾部 | SQL LIMIT + 倒序查询 |
| M4-7 | `state/conversation_db.rs` prune | 受保护尾部也全量载入 | 只查询候选区间 |
| M4-8 | 前端 `live.assistantText` + 工具 200KB raw 双份常驻 | DOM + JS 字符串重复 | 只保留视口内文本，工具 raw 折叠 |
| M4-9 | `meme_collector.rs` 哈希前 `to_vec()` | ~~整份拷贝~~ | ✅ 当前分支已改为 `Sha256::digest(data)` 直接借用，仅复核 |

## 6. M5：大对象 clone 削减

- 请求路径消息历史：改为 `Arc<[ChatMessage]>`，重试不再深拷贝。
- `AppConfig`：见 CPU 方案 C12。
- `platforms/onebot.rs` 每条入站消息两次 AppConfig 深拷贝：普通消息应零拷贝。
- `agent` 图片附件每次从 SQLite 重取并重做 base64：按 run/turn 缓存一次。

## 7. M6：数据库与文件 IO 内存峰值

| # | 现状 | 修法 |
|---|---|---|
| M6-1 | 知识库先整读再校验大小 | stat 先检查，超限直接拒绝 |
| M6-2 | 爬虫 `.text()` 无字节上限 | 用现有 `read_capped` 统一 5 MiB |
| M6-3 | `image_generation/protondb/archlinux` 无上限读响应 | 统一限长读 |
| M6-4 | SQLite 同步阻塞 | 见 CPU 方案 C25/C26 |
| M6-5 | WebUI 附件 32 MiB 在 async handler 搬移 | `spawn_blocking` + 流式写入 |

## 8. M7：进程级内存策略

- renderer worker 已做地址空间限制（release 512 MiB，debug 2 GiB）与 1 小时空闲回收，保持。
- daemon actor 线程栈 16 MiB 是 tokenizer 需要，保持；其他线程降为默认。
- `trim_process_memory()` 的 `malloc_trim` 在回合完成后保留，可在长时间空闲后增加一次。
- 对 `conversation.db` 增加定期 `PRAGMA wal_checkpoint(PASSIVE)` 与 `incremental_vacuum`（低频，不阻塞热路径）。

## 9. 验收

- [ ] 24 小时长跑：RSS 曲线平稳，无单调增长（排除缓存首日预热）。
- [ ] usage-history 轮转后 `usage/stats`、`usage/details` 输出与轮转前一致。
- [ ] 中断回合恢复测试、redo/undo、导出导入全部通过。
- [ ] 大量工具输出会话（4×20k）下内存峰值下降，且请求字节与上下文显示不变。
- [ ] WebUI 长会话滚动内存不随 DOM 线性增长。
