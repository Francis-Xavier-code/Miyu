# 03 · 显存与 3D 渲染优化方案

## 1. 先厘清 GPU 消耗在哪

Miyu 的 Rust 核心**没有自研 3D/GPU 管线**：

- `Cargo.toml` 无 wgpu/vulkan/glow/OpenGL 依赖；
- 终端渲染、RaTeX 公式、QQ 长图渲染、chafa 均为 CPU 位图/文本；
- `renderer` worker 是纯 CPU 进程。

因此显存与 3D 渲染消耗主要来自**宿主程序**：

| 宿主 | GPU/VRAM 消耗 |
|---|---|
| WebUI 浏览器 | DOM 合成层、CSS 动画/滤镜/阴影、大图片解码纹理、KaTeX 字体 |
| Kitty 图形协议 | 图片上传后在终端模拟器侧分配 GPU 纹理 |
| 桌面合成器 | 终端/浏览器窗口合成（Miyu 无法直接控制） |

优化目标：减少 Miyu 向宿主索取的 GPU 资源，而不是在 Rust 里加 GPU 代码。

## 2. G1：压缩 WebUI 静态图片

当前两个嵌入资源明显超尺寸：

| 资源 | 现状 | 实际显示尺寸 |
|---|---|---|
| `pics/miyu-logo.png` | 1254×1254，约 1.9 MiB | 侧栏头像/顶部按钮，约 32–48 px |
| `pics/miyuwallpaper.png` | 3344×1882，约 5.4 MiB | 空状态看板图，约 320–480 px |

浏览器解码后：

- logo 约 6 MiB RGBA 纹理；
- wallpaper 约 25 MiB RGB 纹理；
- 打包二进制和 HTTP 传输各多 7.3 MiB。

**修法**：

1. **不要覆盖 `pics/` 里的源文件**（README、终端演示、外部链接可能继续引用原图）。
2. 在 `web/assets/` 生成仅供 WebUI 使用的显示尺寸 2x/3x 压缩资产：
   - logo：256×256 或 384×384，WebP/PNG quantized；
   - wallpaper：1280×720 或 1440×810，WebP/PNG quantized；
3. 保留 `src/web.rs` 的 `include_bytes!` 与路由名不变，仅改引用的路径/文件；
3. 前端 `<img>` 加 `decoding="async"`、logo 无需 `loading="lazy"`，wallpaper 加 `loading="lazy"`；
4. 空状态不再显示 wallpaper 时，移除 `src` 或切 `display:none`，避免 GPU 保留纹理。

预期：浏览器 GPU 纹理从约 31 MiB 降至 <3 MiB；二进制减少约 6 MiB。

## 3. G2：WebUI 合成层治理

`web/styles.css` 当前有大量动画、filter、box-shadow、transform。逐类处理：

| 现状 | 问题 | 修法 |
|---|---|---|
| `status-pulse`、`session-run-pulse`、`typing-bounce`、`shimmer`、`spin` 等无限动画 | 持续触发合成与重绘 | 只在运行态存在；页面不可见时 `animation-play-state: paused` |
| 对 `filter`、`box-shadow` 做 transition/animation | 每次改变都重绘大纹理 | 改成只动画 `opacity/transform` |
| 多处长阴影卡片 | 增加合成层内存 | 减少层数或使用固定伪元素 |
| 全量 conversation DOM | 每个气泡成为潜在层 | `content-visibility:auto` + `contain: layout style paint` |
| 隐藏的 emptyState 仍可能保留 wallpaper | 背景纹理常驻 | 隐藏时卸载图片 |

新增一个轻量可见性控制器：

```js
document.addEventListener("visibilitychange", () => {
  const paused = document.hidden;
  document.body.classList.toggle("miyu-paused", paused);
});
```

CSS：

```css
body.miyu-paused *,
body.miyu-paused *::before,
body.miyu-paused *::after {
  animation-play-state: paused !important;
}
```

`prefers-reduced-motion: reduce` 时把所有无限动画降级为静态样式。

**功能不变化**：所有状态信息仍通过颜色/文本表达，只减少动画帧与图层。

## 4. G3：Kitty 图形协议上传瘦身

### 4.1 当前尺寸链

- `print_image` 最多 300×200 cells；
- `kitty_image::resize_for_transfer` 将图像缩到 `cols*cell_w` 与 `rows*cell_h`，再 clamp 到 **2048×2048**；
- 常见 8×16 像素 cell 下，300×200 cells 会尝试 2400×3200，最终被 clamp 到 2048×2048 RGBA，约 16 MiB 传输/纹理。

### 4.2 修法

1. 传输上限从固定 2048 改为 `max(2×cell_pixel × max(cols,rows), 512)` 的动态上限；默认显示尺寸只有 300×200 时，不再上传 2048×2048。
2. 对照片类图片保持 2x cell-pixel 超采样；对表情包/小图直接用原始尺寸，避免放大。
3. 同一会话重复发送同一图片时，按 `blake3` 复用已传输 image_id：
   - 维护 `digest → image_id` 的进程内缓存；
   - 若 terminal 可能已清理，通过低开销的 placement-only frame 试探或保守 TTL 淘汰；
   - 缓存必须上限（如 32 条）+ TTL（如 10 分钟），避免无界。
4. LaTeX 公式 `render_math_kitty` 当前 grid 上限 200×8，单帧很小；主要优化点是失败回退避免重复上传（见 5.1）。

**验收**：`kitty + kitty-image` 或 cat image 记录传输帧大小；同一图片第二次发送时不再出现 `a=T` 数据帧。

## 5. G4：LaTeX 与终端渲染 GPU 影响

### 5.1 非 kitty 半块路径

- 半块是普通文本，不走图片协议，**不占 GPU 纹理**；
- 当前固定 9 行导致的性能与观感问题由 `docs/plan/专项-LaTeX渲染问题调查.md` 独立处理；
- 性能上，半块输出每格约 20–30 字节 ANSI，长公式在超宽终端会形成 2–3 KB/行；增加可见列上限（与终端宽度一致）可同时减少 CPU 与终端处理压力。

### 5.2 kitty 路径

- 公式 PNG 以 2x 网格上传，尺寸小，保留；
- 若未来支持图片缓存，公式可优先命中 image_id 缓存（内容稳定，按 tex hash）。

## 6. G5：显存/3D 测量方式

没有自研 GPU 代码，因此使用宿主侧工具：

| 平台 | 命令/工具 |
|---|---|
| NVIDIA | `nvidia-smi --query-gpu=memory.used --format=csv` 或 `nvidia-smi dmon` |
| Intel | `intel_gpu_top` |
| AMD | `radeontop` |
| 浏览器 GPU 内存 | Chrome/Edge `chrome://gpu`、Task Manager GPU memory；Firefox `about:processes` |
| Kitty 图片内存 | 终端内 `ctrl+shift+f1` 调试/占用观察 |

基线流程：

1. 打开 `miyu web`，登录并停留在空状态；
2. 记录浏览器 GPU 进程内存；
3. 进入会话并渲染 10 条含 KaTeX 的回复；
4. 记录增长；
5. 优化后重复同样步骤对比。

## 7. 验收标准

- [ ] WebUI 空状态 GPU 纹理占用较基线下降 ≥60%（主要通过图片降采样）。
- [ ] 无限 CSS 动画在 `document.hidden` 时暂停，`prefers-reduced-motion` 下降级为静态。
- [ ] Kitty 图片传输峰值从 16 MiB 降至动态上限以内。
- [ ] 重复发送同一图片不再重复上传数据帧（缓存命中时）。
- [ ] 功能冒烟：WebUI 空状态图、头像、KaTeX 公式、print_image、show_meme 全部正常。
- [ ] `cargo test` 全绿；终端 PTY 安全测试不受影响。
