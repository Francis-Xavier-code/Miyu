# Miyu 性能优化专项方案（独立于结构性拆分）

> 本目录是独立性能优化方案，**不属于** `docs/plan/README.md` 中 Phase 0–9 的结构性拆分序列。
> 性能改动与模块拆分、死代码清理、LaTeX bug 修复必须分开评审、分开提交。

## 1. 目标

在不改变现有功能、协议、数据格式与用户可见语义的前提下，系统性降低：

1. **CPU 占用**：减少重复计算、O(n²) 热点、async 内同步阻塞、无效轮询与前端全量重渲染。
2. **内存占用**：给所有长期增长的缓冲/缓存加边界，减少大对象深拷贝与重复常驻。
3. **显存占用**：降低 WebUI 浏览器合成层、图片传输与 Kitty 图形协议的 GPU 压力。
4. **3D 渲染消耗**：Miyu Rust 核心没有自研 3D/GPU 路径；重点是 WebUI 合成层、CSS 动画、终端图形协议上传。

## 2. 现状基线

当前主要热点来自 `docs/code-review-2026-08-16.md` 的实测/量化结论，并在本方案中按当前代码符号重新归类。行号会漂移，执行时以符号名与 `rg` 结果为准。

## 3. 总原则

1. **先测量，再优化**：每项优化前记录 CPU/RSS/VRAM 基线；没有测量数字不合并。
2. **语义冻结**：只改执行方式，不改工具结果、消息内容、缓存字节、SSE 事件、提示词与配置语义。
3. **先摘低垂果实**：一批一行级修复收益大、风险低，先做。
4. **异步边界纪律**：文件 IO、SQLite、进程调用、网络请求不得阻塞 actor 单线程 runtime。
5. **边界优先于缓存**：任何新增缓存必须同时设计 TTL/容量上限与失效键。
6. **与拆分方案解耦**：性能优化可以在独立分支推进；若某文件正在做模块拆分，等该文件拆分完成后再改性能，避免冲突。

## 4. 路线图

| 阶段 | 范围 | 目标 |
|---|---|---|
| P0 基线 | 建立 CPU/RSS/VRAM/前端帧率测量脚本 | 可重复验证 |
| P1 CPU 低风险 | 一行级热点、重复计算、clone 削减 | 活跃回合 CPU 明显下降 |
| P2 CPU 结构化 | async 阻塞治理、token 口径、前端渲染 | daemon 不再被单点冻结 |
| P3 内存 | 有界缓存、日志轮转、journal 清理、大对象削减 | 长期 RSS 平稳 |
| P4 GPU/VRAM/3D | WebUI 合成层与动画、Kitty 传输复用 | 浏览器 GPU 内存下降 |
| P5 验收 | 回归、性能门禁、文档 | 资源占用全面降低且无行为变化 |

## 6. 与结构性拆分的关系

- 结构性拆分（Phase 0–9）解决“文件太大致读不懂”；
- 本方案解决“资源占用”；
- 两者正交，但**同一文件不要同时进行拆分和性能修改**。
- 推荐顺序：文件先机械拆分 → 稳定后 → 在该文件上做性能优化。
