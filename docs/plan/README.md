# Miyu 代码拆分与可维护性重构方案

> 本方案由 DeepSeek 基于对当前 Miyu 源码（0.4.x）的逐模块走查整理，属于**临时施工方案**；正式方案仍需项目维护者评审后执行。本方案只做结构性拆分与接口梳理，**目标是不改变任何现有功能、协议、数据格式与用户可见行为**。

> 行号说明：文档中的 `file:line` 是 2026-08-17 `token-optimization` 分支的评审快照；执行任何阶段前先 `rg -n '<符号>' src` 重新定位。

## 一、方案要解决什么

当前 Miyu 功能完整，但存在四类结构性问题：

1. **巨型文件**：`cli.rs`（约 16.5k 行）、`web.rs`（约 12.8k 行）、`onebot.rs`（约 10.5k 行）、`agent/mod.rs`（约 9.6k 行）、`config.rs`（约 8.7k 行）、`openai_compatible.rs`（约 8.6k 行）等，阅读与修改成本极高。
2. **跨层依赖与循环**：`platforms → web`（平台层依赖 Web/daemon 内部类型）、`web → cli`（daemon 入口依赖 CLI 参数与工具注册）、`tools → platforms`、`state ↔ memory` 等，导致牵一发动全身。
3. **测试与实现同文件**：大文件里混着数千行 `#[cfg(test)]` 测试，生产逻辑与测试相互干扰。
4. **缺少清晰分层**：类型、协议、执行、呈现混在一起，新增平台/协议/工具需要同时理解多个超大文件。
5. **死代码被全局豁免掩盖**：`main.rs` 的 `#![allow(dead_code)]` 让约 100+ 处未使用代码不可见，清理工作必须在拆分后专项执行。

## 二、总原则（每个阶段都必须满足）

1. **零行为变化**：纯机械移动 + 可见性调整 + 少量接口抽取；不顺手改业务逻辑、不修 bug、不优化。
2. **每步可编译、可测试**：任何一次提交都必须 `cargo check`、`cargo test` 通过；禁止“先拆坏，后面再修”。
3. **一次只拆一个文件/一个方向**：每个 PR 只做一组内聚移动，便于 review 和 `git bisect`。
4. **先立安全网，再动刀**：先建立基线快照、机械校验脚本和依赖方向门禁，再进行拆分。
5. **保留字节级缓存契约**：消息组装、工具目录、提示词顺序等**不得因文件移动而改变任何字节**；所有移动必须是 `git mv` + `use` 路径调整。
6. **测试跟着实现走**：实现函数搬到新文件时，对应的 `#[cfg(test)] mod tests` 内容也同步搬走，禁止把测试堆在旧文件里。
7. **死代码后置处理**：拆分阶段只做“原样搬运”，禁止顺手删代码；全部移动稳定后按 [13-死代码清理计划](13-死代码清理计划.md) 专项清理。

## 三、路线图总览

| 阶段 | 内容 | 目标 | 风险 |
|---|---|---|---|
| Phase 0 | 基线、安全网、分支策略 | 建立可回滚的起点 | 极低 |
| Phase 1 | 引入 `lib.rs`，打破 `platforms→web`、`web→cli` 循环 | 建立干净分层 | 低 |
| Phase 2 | 拆分 `cli.rs` | 每个文件 < 约 1500 行 | 低（机械） |
| Phase 3 | 拆分 `web.rs` | 每个文件 < 约 1500 行 | 中 |
| Phase 4 | 拆分 `agent/`、`llm/openai_compatible.rs` | 协议/工具循环可独立阅读 | 中 |
| Phase 5 | 拆分 `config.rs`、`config_tui.rs` | 配置结构按领域聚合 | 低 |
| Phase 6 | 拆分 `state/` | 数据访问按聚合分离 | 中 |
| Phase 7 | 拆分 `platforms/onebot.rs` 与插件 | 协议适配可扩展 | 中 |
| Phase 8 | 收尾：`tools/`、`render/`、`memory/` 小文件清理 | 模块边界收敛 | 低 |
| Phase 8.5 | 死代码专项：删除/测试化/标注约 100+ 处，移除全局 `allow(dead_code)` | 让编译器重新发现腐化 | 低（逐项可回滚） |
| Phase 9 | 架构门禁、文档、可选 workspace 评估 | 防止退化 | 低 |

## 五、预计工作量与执行建议

- 每个 Phase 约 1–4 个 PR；全部落地建议控制在 8–12 周，宁可慢，不要混入行为改动。
- 优先级：**Phase 0 → 1 → 2 → 3** 是收益最大、最机械的部分；Phase 8.5 死代码清理可以按模块穿插，但**不得**在对应模块拆分完成前开始。
- 建议每完成一个 Phase 就合并并实际跑一轮：`cargo test`、终端 REPL 冒烟、WebUI 冒烟、QQ/NapCat 冒烟、`miyu export/import` 冒烟。
