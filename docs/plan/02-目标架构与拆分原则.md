# 02 · 目标架构与拆分原则

## 1. 目标：先模块化，后谈多 crate

本方案分两层：

- **主线（本方案落地范围）**：保持单一 Rust crate，把超大文件拆成目录内的多个小文件，并用 `pub(crate)`/`pub(super)` 收紧可见性。收益明显、风险可控、可随时暂停。
- **远期（仅评估，不在本方案强行执行）**：当目录边界稳定后，再评估拆成 `miyu`（bin）+ `miyu-core`（lib）或多个 workspace crate。过早拆 crate 会把当前 180k 行单 crate 的模块循环变成 crate 循环，编译和迁移成本反而更高。

## 2. 目标分层

```
┌─────────────────────────────────────────────────────┐
│ 呈现层  cli/  web/  shell/  render/  config_tui/     │
├─────────────────────────────────────────────────────┤
│ 宿主层  runtime/  daemon.rs  ipc.rs                  │
├─────────────────────────────────────────────────────┤
│ 编排层  agent/                                        │
├─────────────────────────────────────────────────────┤
│ 领域层  tools/  memory/  state/  llm/  skills/        │
│         transfer/  default_kb/  persona_hint/        │
├─────────────────────────────────────────────────────┤
│ 适配层  platforms/（OneBot + 插件）                   │
├─────────────────────────────────────────────────────┤
│ 基础层  paths.rs  config/  i18n.rs  logging.rs        │
│         token_counter.rs  json_extract.rs  ...       │
└─────────────────────────────────────────────────────┘
```

依赖规则（用架构测试强制）：

1. **基础层不依赖上层**：`paths/config/i18n/logging` 不得 import 其他业务模块。
2. **领域层不依赖呈现层与宿主层**：`tools/memory/state/llm` 不得 import `cli/web/runtime/daemon`。
3. **适配层不依赖呈现层**：`platforms` 不得 import `web/cli/config_tui/render`。
4. **宿主层可依赖领域层**，但领域层不得反向依赖宿主层。
5. **类型-only 依赖下放**：`PlatformPrincipal`、`PlatformContextImageRef`、`PlatformImageData`、`PlatformContextFileRef` 等纯数据类型下沉到独立模块，供 `agent/tools/memory` 使用，而无需引入平台运行逻辑。
6. **工具注册方向单向**：`platforms` 可调 `tools::ToolRegistry` 注册平台工具；`tools` 不得依赖 `platforms` 的执行/发送逻辑，需要时通过 trait 回调。
7. **死代码只在专项阶段处理**：拆分过程中保持“搬得一模一样”；任何未使用符号等 Phase 8.5 统一处置，见 [13-死代码清理计划](13-死代码清理计划.md)。

## 4. 文件规模阈值

| 阈值 | 要求 |
|---|---|
| 理想 | 单文件 ≤ 800 行生产代码 |
| 可接受 | 单文件 ≤ 1500 行生产代码 |
| 红色线 | 拆分前若文件 > 3000 行，必须先拆，再继续加功能 |

## 5. 命名与导出规范

- 模块目录的入口统一 `mod.rs`，禁止在 `mod.rs` 里继续堆 500+ 行业务。
- 新文件之间共享类型用 `pub(super)`；给其他模块的类型用 `pub(crate)`；真正稳定的公共 API 才 `pub`。
- 函数名、常量名、日志文案、错误文案**一律不动**，避免快照测试和用户脚本依赖破坏。
- 每个文件顶部写一行注释说明职责；移动代码时保留原注释与行号引用（行号变化在 PR 描述中说明）。

## 6. 死代码红线

- 拆分 PR 中禁止出现“顺便删除未使用函数/字段/模块”的 diff。
- 每个 Phase 结束后用 `RUSTFLAGS='--force-warn=dead_code' cargo check` 记录告警数量；只允许因“移动后可见性变化”产生的新告警，不允许业务删除。
- 最终死代码处置只有四类：删除（D1）、测试化（D2）、标注保留（D3）、语义修复/废弃（D4），细则见 13 号文档。

## 7. 拆分动作模板（每阶段通用）

对每个目标文件执行：

1. `git mv` 或新增模块目录。
2. 从原文件剪切相关类型/函数/测试块。
3. 补 `use`、把私有可见性改为 `pub(super)`/`pub(crate)`。
4. `cargo fmt`、`cargo check`、`cargo test <受影响的模块>`。
5. 运行 Phase 0 的机械回归脚本。
6. 提交：`refactor(<module>): split <source> into <target> (no behavior change)`。
