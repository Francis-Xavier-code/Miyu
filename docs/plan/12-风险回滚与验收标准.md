# 12 · 风险、回滚与验收标准

## 一、风险清单与对策

| 风险 | 触发条件 | 对策 |
|---|---|---|
| 字节前缀缓存退化 | 移动 agent/llm/tools 时调整了消息组装/工具目录序列化 | 每阶段跑缓存回归；涉及 agent/llm/tools 的 PR 加 mock 前缀断言 |
| 数据库不兼容 | 改变 turn 固定列序、迁移函数、表名常量 | `state/db/schema.rs` 加锁定注释；迁移 v1–v24 只读不改；旧 DB 逐版升级测试 |
| IPC/协议不兼容 | 改 `ipc.rs` 枚举或帧格式 | 本方案不修改任何 `Command` tag、字段顺序、错误文案；只移动文件 |
| QQ 行为变化 | 改 CQ 解析顺序、连接代际、发送拆条 | onebot 拆分按函数整体搬迁；跑 NapCat 真机冒烟 |
| WebUI 前端/后端事件脱节 | 改 SSE 事件名 | 本方案不重命名事件；`EVENT_NAMES` 与 `RunEventMapper` 只在同 PR 同文件移动时保持原字符串 |
| 配置读写损坏 | serde 默认值/字段名/旧键迁移变化 | 保存基线 `config.jsonc` 快照，diff 默认配置；`config validate` 冒烟 |
| 测试丢失 | 移动测试块时遗漏 | 每次移动前后对比 `cargo test -- --list` 数量；测试数量不得减少 |
| 合并冲突 | 拆分分支与 main 并行开发 | 每个 Phase 小 PR，尽快合并；冲突时优先重新执行机械移动 |
| 回归难定位 | 一次 PR 太大 | 每 PR 只拆一个逻辑单元；commit message 标 `refactor(<module>)` |
| 删错“看起来没用”的代码 | 死代码被 `allow(dead_code)` 掩盖，人工判断失误 | 强制 lint 报告 + `rg` 引用复核；字段先查 serde/IPC/DB 契约；删除 PR 单模块可回滚 |
| 清理后测试数量下降 | 测试专用函数被误删或测试模块漏搬 | 每次清理前后对比 `cargo test -- --list`；D2 函数只 `#[cfg(test)]` 不删除 |

## 二、回滚策略

1. **单 PR 回滚**：`git revert <commit>` 即可；因每个 PR 只做结构移动，revert 不会产生业务冲突。
2. **阶段回滚**：每个 Phase 分支合并前打 tag：`refactor-phase-N-before`；失败则 `git reset --hard` 到 tag 并重新执行。
3. **行为回滚**：保留 Phase 0 基线二进制；如任何阶段出现无法解释的行为差异，用基线二进制跑同一黑盒脚本对比，定位是该阶段的代码移动还是环境/上游变化。
4. **不推进原则**：若某个 Phase 连续出现两次需要回滚的 bug，暂停该 Phase，重新拆小或跳过，先推进其他低风险 Phase。

## 三、验收标准（总）

### 结构验收

- [ ] 不存在 >3000 行的生产源文件（测试模块除外）。
- [ ] `cli/web/config/config_tui/onebot/openai_compatible/agent/conversation_db` 均已成目录。
- [ ] 依赖门禁全部通过：

```text
platforms → web / cli：禁止
web → cli：禁止
tools → platforms：禁止（除类型 trait）
agent/memory → platforms 运行时：禁止
render → tools 执行：禁止
state ↔ memory 直接交叉：禁止
```

### 行为验收

- [ ] `cargo test` 全绿，测试数量 ≥ 基线（删除 D1 死代码附带的废弃测试除外，需在 PR 说明）。
- [ ] 完成 Phase 0.5 后 `cargo fmt --check` 通过；在此之前仅要求 PR 触及文件通过 `rustfmt --check`。
- [ ] `cargo test` 与格式化后的基线一致（无新增失败，已知环境项需有 issue 跟踪）。
- [ ] `RUSTFLAGS='--force-warn=dead_code' cargo check --all-targets` 零告警（白名单除外）。
- [ ] `miyu -h`、各子命令帮助与基线逐字一致。
- [ ] 默认 `config.jsonc`、`miyu export --dry-run` 清单、`tool-call --list` 与基线一致。
- [ ] 终端 REPL、WebUI、QQ、shell hook、daemon、导出/导入冒烟通过。
- [ ] 固定会话两轮请求的 `cache_read` 与基线一致（在相同 provider 条件下）。
- [ ] 旧数据库迁移、旧导出归档导入通过。

### 可维护性验收

- [ ] 新增一个工具不需要阅读 `cli.rs` 或 `web.rs`；按新工具指南最多改 5 个文件。
- [ ] 新增一个协议（如 Gemini）只需在 `llm/openai_compatible/` 加一个文件并在 `mod.rs` 登记。
- [ ] 新增一个平台（如 Telegram）只需在 `platforms/` 加一个目录，实现 `PlatformAdapter`，不触碰 `web` 内部。
- [ ] 新贡献者能在 30 分钟内从 `docs/wiki/14-参与开发.md` 和模块注释找到所有关键入口。

## 四、完成定义（DoD）

本方案视为完成，当且仅当：

1. Phase 0–8 与 Phase 8.5 死代码专项全部按顺序合入 `main`；
2. 上述结构与行为验收全部通过；
3. CI 中架构门禁与规模门禁为 required；
4. `docs/wiki` 和根 README 中的路径/行号已更新；
5. 发布一个正常版本并至少运行一周无因重构引入的回归。
